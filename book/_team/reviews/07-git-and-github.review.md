## Findings

1. **major** - History overstated in 7.7: "the merge decision rested with a senior technical manager role played by an AI review agent, with a product-owner agent covering the product side". The dossier says the technical-manager reviewer wrote "I recommend MERGE of #5 into main, subject to the product owner's approval" (reviews.md, review at 6cf17fa). The merge decision belonged to the project's human owner; the AI agents recommended. Fix: "the technical-manager reviewer (an AI review agent) recommended when to merge, and the project's owner made the decision". (The source comment cites "decisions.md (TM as merge gatekeeper)"; I found no such statement there, so the claim needs a real source or removal.)
2. **minor** - Windows/Git portability: the sample `git status` output says "On branch main", but on Git older than 2.28 or with an unconfigured system `git init` creates `master`. Use `git init -b main` (or `git branch -M main`) in 7.3 and mention it, otherwise 7.6 (`git switch main`) fails for some readers.
3. **minor** - 7.4 names the repository owner's GitHub account (`Sriram-Codes-SW/secure-doc-viewer`) in reader-facing text. It is a public handle, not an email, but the repository is private and the book is meant to outlive access arrangements; the editor should decide whether to keep the name or say "the project's repository (address given in the front matter)". Also give the promised front-matter pointer (the setup chapter) for how readers "were given" a copy.
4. **minor** - 7.5: "the code at each tag is the cumulative state at that merge" is right. Add that `git checkout book-mN` on the reader's clone requires that the tags were fetched (`git fetch --tags`) if they cloned with a shallow or partial option; one sentence.
5. **minor** - 7.4 sample log shows `a27e069 Merge pull request #12 from ...` at the top; it is the tip of `main` at m6 only if the reader has not switched to `book/draft` or a newer main. Say "at the time of `book-m6-final`".
