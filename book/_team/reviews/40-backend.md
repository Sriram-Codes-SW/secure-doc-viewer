# Review of Chapter 40 (Spring/Java side): would the described changes work?

Reviewer: writer-backend. Scope: `book/part-7-cloud/40-aws-production.md` (draft), checked against the code, `frontend/nginx.conf`, `Dockerfile` and `docker-compose.yml` at `book-m6-final`. I did not run any of this; findings marked "verify" rest on Spring, Spring Session or ElastiCache behavior I know from their documentation and should be confirmed against the versions you cite before the chapter says them as fact. I did not edit the chapter.

## Verdict

The chapter's overall shape is sound and mostly matches the code: the database pointer as the atomic switch, `TileWorkLimiter` staying local, the cookie CSRF repository needing no change, the last-address forwarded-header rule, and readiness rather than full health for the ALB are all correct. But one change as written **would break an existing security feature** (Blocker), and several other changes are under-specified in ways that would make an implementer stumble or ship a regression (Majors).

## Blocker

**B1. Swapping in the Spring Session registry breaks the admin Sessions page, revoke-by-handle, and "role change / password reset ends the user's sessions".** (Section 40.10, Listing 40.6, the "In this project" row for `SecurityConfig.java`.)

`SessionAdministration` (`book-m6-final`) does all three of `list`, `revoke(handle)` and `revokeAllFor(username, ...)` by iterating `registry.getAllPrincipals()`. Spring Session's `SpringSessionBackedSessionRegistry` cannot enumerate all principals (verify: its `getAllPrincipals()` is documented as unsupported and throws `UnsupportedOperationException`); it can only return the sessions of a *named* principal, and only with the indexed Redis repository. So after the swap the admin page fails, an administrator cannot revoke a session by its handle, and `UserAdminController.update`, `resetPassword` and `AuthController.changePassword` (which call `revokeAllFor`) fail or silently stop revoking. The last is a security property (Chapter 16), not just a convenience.

The chapter's sentence "needs the *indexed* Redis repository so one user's sessions can be found" is true but hides the problem: the code never asks for one user's sessions, it asks for every principal.

Suggested wording (replace the `SessionRegistry` sentences in 40.10): "`SessionAdministration` enumerates every principal in the registry, which Spring Session's registry does not support. Change it to iterate the user names from the database (`AppUserRepository`) and ask the registry for each user's sessions, or call `FindByIndexNameSessionRepository.findByPrincipalName(username)` directly; `revokeAllFor` already knows the user name. Then re-run `SecurityIntegrationTest` cases `adminSessionListUsesHandlesNotSessionIds`, `revokedSessionIsRejectedOnItsNextRequest`, `anAdminCanSignAUserOutEverywhere` and `roleChangeEndsTheUsersExistingSessions` against a real Redis (Testcontainers)." Also update the "In this project" table: `SessionAdministration.java` changes, not only `SecurityConfig.java`.

Related behavior change (Minor, say it): a revoked session's record is deleted from Redis, so its next request arrives with an unknown cookie and gets the plain `401 Sign-in required.`, not the `Your session has ended. Please sign in again.` message that `SecurityErrorResponses.onExpiredSessionDetected` writes today.

## Major

**M1. Session events, `SessionMetadata`, and the ElastiCache `CONFIG` problem.** `SessionMetadata` listens for Spring Security's `SessionDestroyedEvent` and `HttpSessionIdChangedEvent`, which the `HttpSessionEventPublisher` bean (Listing 40.6) forwards from the *servlet container*. Once sessions live in Spring Session, the container no longer owns them, so those events stop arriving: the `bySessionId` map would grow without bound and hold stale entries (the chapter says it "moves into the session or the store", which is right, but should say why it can't stay). Spring Session's own events need Redis keyspace notifications; Spring Session normally enables them by sending a `CONFIG` command at startup, and ElastiCache does not permit `CONFIG` (verify), so the well-known symptom is a startup failure unless the configure action is set to none and `notify-keyspace-events` is set in a parameter group. The chapter says only "details this chapter did not verify"; because this is the most likely first failure, name it and give the two settings to check (Boot: `spring.session.redis.configure-action`, and the cache parameter group). Also state the properties the reader will need: the starter, `spring.session.redis.repository-type=indexed`, and the Redis host/TLS/auth settings (names differ across Boot lines; check Boot 4.1).

**M2. The "reserve the version first, upload, then switch" replace (Figure 40.3) can move the pointer backwards.** Today the row lock serializes replaces, so `nextVersion = current + 1` is always the newest (`DocumentService.replaceFile`), and `MySqlIntegrationTest.concurrentReplacementsAreSerialisedByTheRowLock` asserts the end state (`tile_version` 3, only `v3` on disk). With reservation outside the lock, two publishers reserve v2 and v3, upload both, and can switch in either order; if v3 switches first and v2 second, the document points back at v2 and v3 is orphaned. Say: reserve numbers from a monotonic counter that is never reused, and at switch time under the lock switch only if the reserved number is greater than the current one (otherwise discard your own upload). The never-reused rule also matters for F2 in Chapter 33's history: today `replaceFile` deletes any leftover `vN` under the lock before committing; with `If-None-Match: *` a leftover key from a failed attempt would answer `412` on retry unless retries use a *new* number. State that, and note the janitor (not the retry) cleans abandoned prefixes. The chapter's "probably needing a new Flyway migration" should say what column (a counter on `document`).

**M3. "One Lua script" is the right idea, but the described script covers only a fraction of what `LoginThrottle` and `TileRateLimiter` do.** From the code:
- `reserve` checks three keys (`account:{user}|{ip}`, `ip:{ip}`, `user:{user}`; the third only when the device is not recognised) and appends to all three; the result must also carry which rule refused and a `Retry-After` computed from the oldest counted failure (`lockedFor`). Listing 40.9 (the tile limiter sketch) is fine, but no login sketch is given and the prose says only "checks the three keys".
- `succeeded` deletes the whole account+ip key and removes *one specific* provisional entry from the other two (`removeLastOccurrence`); `TileRateLimiter.refund` does the same by value. In Redis each entry needs a **unique member id** returned to the caller (two attempts can share a millisecond), so `reserve` and `recordAndEnforce` change their return type from `Instant`, and `TileController` (which holds `counted`) changes too.
- `unlock(username)` removes every key with the prefix `account:{username}|`, and `isLocked(username)` scans keys by prefix (admin user list). Redis has no prefix delete; use a per-user index set or hash tags.
- **Cluster mode:** a script may only touch keys in one hash slot. The three login keys depend on different values (user+ip, ip, user), so they cannot share a slot; in ElastiCache use a cluster-mode-*disabled* replication group (single shard), or the script fails with a cross-slot error. Say so.
- Use the store's clock (or one agreed source), not each task's `Instant.now()`.
- Replace the in-memory `sweep()` methods with key expiry equal to the window.
- **Failure policy:** the code has no answer to "the store is unreachable". Decide and write down: fail closed for sign-in (refuse) or open (accept and log) and the same for tile counters, and test it.

**M4. Rolling deploys kill uploads mid-render: no graceful shutdown is configured.** `application.yml` and `docker-compose.yml` set no `server.shutdown` (Spring Boot's default is immediate) and no stop grace period. An upload renders inside the request for up to `render-timeout` (3 minutes). On an ECS rolling update or scale-in, a task that stops immediately drops the request (client sees `502`), leaves a staging folder for the janitor (which only removes it after 1 hour), and any tiles already committed without a row are cleaned by the same janitor. Suggested addition to 40.5/40.16: `server.shutdown: graceful`, `spring.lifecycle.timeout-per-shutdown-phase` at least as long as the longest render, the ECS container stop timeout and the target group's deregistration delay set to match (verify current limits), and note that the readiness endpoint the chapter already recommends flips to refusing traffic during shutdown, which is what lets the ALB drain the task first.

**M5. JVM memory and task memory with a sidecar.** The `Dockerfile` sets `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75`, and Compose gives `app` 1536m and nginx 128m as separate limits. In one Fargate task the two containers share the task's memory unless the task definition gives each a `memory` limit; a JVM without its own limit sizes its heap from the whole task (75% of, say, 2 GB is 1.5 GB), leaving too little for nginx, metaspace, thread stacks and PDFBox temp-file buffers. Add: set a hard container memory for the app (Compose's 1536m is the tested value) and a small one for nginx, and size the task above their sum; remember `max-concurrent-renders` is per task (two tasks allow four renders at once), and one page at the pixel limit is about 160 MB of pixels.

**M6. Connection-pool sizing must count the nested `REQUIRES_NEW` audit connection.** Section 40.7 correctly says to multiply the pool by the number of tasks against the RDS limit, but it omits a code fact that changes the arithmetic: `DocumentService` calls `audit.recordAtMostEvery(...)` (through `recordDenied` in `requireViewable`) *inside* `tx.execute`, and `AuditLogService` opens a second transaction (`PROPAGATION_REQUIRES_NEW`), so that request holds two connections at once. With a small pool (which the RDS limit encourages), enough concurrent denials can hold every connection while each waits for a second one, until Hikari's connection timeout (verify: 30 s by default). Add a sentence to 40.7: size the pool for two connections per concurrently denying request, or make the audit write happen after the outer transaction; and note that each tile request also does one short database read (`tileAccessIfViewable`), so tile traffic is database traffic.

**M7. nginx: the `map` cannot match subnets, and the protocol header must be trusted from the ALB or the CSRF cookie loses `Secure`.** Chapter 40.6 says to "trust the ALB's subnets in `set_real_ip_from` *and the `map`*". `set_real_ip_from` accepts CIDR ranges, but `map $realip_remote_addr $forwarded_proto` (Listing 40.1) compares the address as a string (an exact address today, `172.28.0.11`); it needs a `geo` block or a regular-expression map to match a subnet. Second, that map falls back to `$scheme` (`http`, since the ALB talks HTTP to nginx) for any peer it doesn't recognise, so unless the map trusts the ALB and passes its `X-Forwarded-Proto`, the app sees `http`. `SecurityConfig.csrfTokenRepository` customizes only `sameSite` and `path`, so the `XSRF-TOKEN` cookie's `Secure` attribute follows `request.isSecure()` (verify in `CookieCsrfTokenRepository`); the session cookie is safe because `SESSION_COOKIE_SECURE=true` forces it, but the CSRF cookie would go out without `Secure`. The chapter names only the session cookie. Add: check `Set-Cookie` for both cookies through the real ALB, and either fix the map or set `secure(true)` in the cookie customizer. Also say `FORWARD_HEADERS_STRATEGY=native` must still be set on the task (the default in `application.yml` is `none`); Section 40.6 says only "unset `TRUSTED_PROXY_REGEX`".

**M8. Flyway "as a one-off task" needs a mechanism, and the bootstrap admin races on first start.** Spring Boot has no "migrate and exit" mode. Running the app image as the one-off would start Tomcat, the schedulers and `BootstrapAdmin` (which creates the first administrator and logs a generated password). Service tasks need `spring.flyway.enabled=false` (or a runtime user without DDL rights, which would otherwise fail at startup), and the migration step should be the Flyway command-line container or the app under a dedicated profile that disables the web server, scheduling and the bootstrap runner. Boot's `spring.flyway.user`/`password` (verify names) let migration and runtime users differ. Also: `BootstrapAdmin.run` does `hasAnyUsers()` then `create(...)` with no handling of a duplicate; two tasks starting together against an empty database can both try, and one fails its startup on the unique constraint. Run the bootstrap in the one-off, or make it tolerate the race. And a rolling deploy runs old and new code against the same schema, so migrations must be backward compatible for one release (add before you remove).

**M9. Scheduled jobs: which can be switched off per task, and the one-off task problem.** `AuditLogService.purgeExpired` and `KnownDevices.purgeExpired` have property-driven crons (`secure-doc-viewer.audit-retention-cron`, `secure-doc-viewer.known-device-purge-cron`), so on the service tasks they can be disabled by setting the property to Spring's disabled-cron value `-` (verify), with no code change. `StorageJanitor.sweep` uses fixed strings (`initialDelayString = "PT2M"`, `fixedDelayString = "PT6H"`), so it cannot be turned off per task without a code change (for example a conditional bean or a property). And `@EnableScheduling` sits on `SecureDocViewerApplication`, so a "one-off task from the same image" runs every scheduler unless the app gains a profile or flag. The chapter's "a change to how the app starts" is right; list these specifics. Also correct the list of jobs: there are six `@Scheduled` methods (add `TileRateLimiter.sweep`, every 5 minutes), of which the in-memory ones (`LoginThrottle.sweep`, `TileRateLimiter.sweep`, `AuditLogService.sweepThrottled`) stay per task (or disappear if the counters move to Redis).

## Minor

- **m1. Keep-alive advice names the wrong component.** In the sidecar layout the ALB talks to nginx, not Tomcat. `nginx.conf` sets no `keepalive_timeout`, so nginx's default (75 seconds, verify) already exceeds the ALB's 60-second idle timeout, as AWS advises; Tomcat's `server.tomcat.keep-alive-timeout` matters only if you send the ALB straight to the app (the chapter's later "drop nginx" case) or enable upstream keep-alive in nginx. Rewrite the sentence in 40.5 accordingly, and keep the `proxy_read_timeout 300s`, `client_max_body_size 51m` values in mind: a raised ALB idle timeout must exceed 3 minutes plus upload time.
- **m2. Add the positives explicitly** so a reader doesn't over-change: the cookie CSRF repository is stateless (`CookieCsrfTokenRepository`), so it needs no change on multiple tasks; `ChangeSessionIdAuthenticationStrategy` works with Spring Session (id rotation at sign-in still defeats fixation, and `SessionKeys.tileBinding` derives from the rotated id); `SessionLifetimeFilter` keeps working because the 12-hour rule is an attribute (`SIGNED_IN_AT`) checked by the filter, independent of the Redis TTL, which follows the idle timeout (`server.servlet.session.timeout` 30m; Boot's Spring Session timeout falls back to it, verify).
- **m3. The session cookie is written by Spring Session's cookie serializer, not Tomcat.** Boot maps `server.servlet.session.cookie.*` onto it (verify), so name, `HttpOnly`, `SameSite=Strict` and `Secure` should survive, but say "check `Set-Cookie` after the switch".
- **m4. Serialization and upgrades.** Spring Session's default JDK serialization needs every session attribute to be `Serializable` (the `SecurityContext`, the `Boolean` password-change flag and the `Instant` all are); a JSON serializer needs the Spring Security and java-time modules. Note that JDK-serialized sessions can fail to load after a Spring Security upgrade changes a class, ending everyone's session at a deploy. Also say the stored security context should not contain the password hash (Spring Security erases credentials after authentication by default; verify by inspecting one stored session).
- **m5. Encrypt the new hops.** Section 40.7 and 40.10 do not mention TLS to RDS or ElastiCache. The JDBC URL in `application.yml` has no `sslMode`; add `sslMode=VERIFY_CA` (or at least `REQUIRED`) with the RDS CA bundle, and Redis TLS plus an auth token, since session data and counters are sensitive. This belongs beside the security review in 40.19.
- **m6. Janitor on S3 needs an "age" replacement.** `StorageJanitor` decides "old enough that no upload can be in flight" from directory modification time (`Files.getLastModifiedTime`); S3 prefixes have none. Use the newest object's `LastModified` under the prefix, and mention the listing cost of a full-bucket sweep every six hours.
- **m7. `commit` runs inside the transaction only for replace.** Section 40.8 says "Today `tiles.commit(...)` runs inside the transaction"; that is true of `replaceFile`; `upload` commits (version 1 of a new id) *before* its short transaction. Say "in `replaceFile`".
- **m8. Staging is moved today, uploaded tomorrow.** Local `commit` moves the staging folder; an S3 implementation copies and must then `discard` the staging folder itself, and `deleteVersion`/`deleteTiles` must list-and-delete in batches (roughly 6,000 keys for a 500-page document).
- **m9. Listing 40.4 is accurate** against `TileGenerationService.commit` and `loadRawTile` at `book-m6-final` (I compared the text). Listings 40.6 to 40.8 also match the code I read.
- **m10. Things I checked and found correct:** the last address wins with `real_ip_recursive off`; Tomcat's default trusted-proxy list is wider than the project needs; `TileWorkLimiter` should stay local (it is a per-task `Semaphore`, default twice the CPU count) and `max-concurrent-tile-renders` should be set explicitly; Hikari's default pool size is 10; `management.endpoint.health.probes.enabled` is already true, `SecurityConfig` already permits `/actuator/health/**`, and `nginx.conf` proxies only the exact path `/actuator/health`, so a readiness location must be added, as the chapter says; the `/actuator/health` aggregate would include the database and would restart healthy tasks during a failover.

## Summary for the editor

Top issues: B1 (admin session features break with the Spring Session registry), M1 (session events and ElastiCache `CONFIG`), M2 (replace reorder can move the version pointer backwards), M3 (shared counters need unique ids, prefix operations, single-slot keys and a failure policy), M4 (no graceful shutdown for 3-minute renders), M7 (nginx `map` cannot match a subnet; CSRF cookie `Secure` depends on the forwarded protocol).
