## Findings

1. **major** - Security explanation likely inaccurate in 23.8. The chapter says that without `safeReturnUrl` the victim "would land on `evil.example`". But the login component follows `returnUrl` with Angular's `router.navigateByUrl(returnUrl)`, which parses the string as an address inside the application and never leaves the page's origin; a value such as `//evil.example/fake` becomes route segments (and, with no matching route, falls to the catch-all). The attack described (off-site redirect) would need code like `window.location.href = returnUrl`. The source comment ("a crafted ?returnUrl=//evil.example must not redirect off-site") states the intent, but the book must not teach an exploit path that does not exist. Fix: verify by a small experiment or spec (call `navigateByUrl('//evil.example')` in a test app and see where it goes), then either (a) reword 23.8 as defense in depth ("the check keeps the value an in-app path, so it cannot become an off-site redirect if the code later changes to a full page load, and keeps odd values from reaching the router"), or (b) show the real vulnerable pattern. Keep Table 23.2; it is correct as a description of the function. Also state that Chapter 26/32 do not claim an incident here (the chapter correctly says none occurred).
