## Majors

1. **Major - 40.6, same-task layout: the instruction to "unset `TRUSTED_PROXY_REGEX`" omits `FORWARD_HEADERS_STRATEGY`.** `application.yml` defaults `forward-headers-strategy` to `none`, which ignores `X-Forwarded-For` entirely (the file's own comment says so). If the reader unsets the regex as instructed and forgets that Listing 40.2 also sets `FORWARD_HEADERS_STRATEGY: native`, every request appears to come from 127.0.0.1: all readers share one sign-in throttle address and the audit log records loopback. That is the silent failure mode of Chapter 33's Exercise 33.3, in the very section about the forwarded-header incident. Fix: say "keep `FORWARD_HEADERS_STRATEGY=native`; only `TRUSTED_PROXY_REGEX` is left at its default", and repeat the forged-header test (the chapter already asks for it).
2. **Major - 40.6: "Trust the ALB's subnets in `set_real_ip_from` and the `map`".** `set_real_ip_from` accepts CIDR ranges, but the `map $realip_remote_addr $forwarded_proto { 172.28.0.11 ...; }` in Listing 40.1 matches exact strings (or `~` regular expressions). A subnet written in that map never matches, so `$forwarded_proto` falls to `$scheme` (`http`, since nginx listens on plain HTTP), the ALB's `X-Forwarded-Proto: https` is discarded, and the app sees plain HTTP behind an HTTPS front door. Fix: say to use a regular-expression key for the ALB's subnets in the `map` (or a `geo` block), and add that check to the forged-header test (check that `X-Forwarded-Proto` still arrives as `https`).
3. **Major - 40.8, 40.15 and Listing 40.13 disagree about deleting superseded versions.** 40.8 says the app "must delete the old prefix itself (as `deleteVersion` does)", and Figure 40.3 ends with "delete the previous version, best effort", immediately after the switch. 40.15 says "never delete a superseded prefix until every database backup that references it has aged out", and relies on "delayed deletion". Both cannot hold. With S3 versioning on, an app-side delete only adds a delete marker and leaves the objects as noncurrent versions, which Listing 40.13 then expires after 30 days, while RDS backups can be retained for up to 35 days, so a restore of an old backup can point at tiles that are gone. The chapter never connects these. Fix: state the rule explicitly (noncurrent-version expiry must be at least the longest database backup retention, and the janitor safety net must not permanently delete current-or-referenced prefixes), or defer the app's delete; change the placeholder `noncurrent_days = 30` note accordingly.

## Minors

4. **Minor - S3 key layout is inconsistent.** 40.8 shows the key `doc/v3/page-0/tile-0_0.png`, but Listing 40.11's policy and Listing 40.13's lifecycle rule use the prefix `tiles/`, so the example key would be outside both. Use `tiles/{docId}/v{n}/page-{p}/tile-{r}_{c}.png` throughout.
5. **Minor - 40.8: "Today `tiles.commit(...)` runs inside the transaction".** True of `replaceFile`; in `upload` (Listing 17.8) `commit` runs before the transaction. Say "in a replace".
6. **Minor - 40.7: "Run `MySqlIntegrationTest` against a throwaway RDS instance".** The test starts its own MySQL container through Testcontainers; running it against RDS would need adapting the test. Say "adapt the test to point at a throwaway RDS instance of the same version".
7. **Minor - 40.5, idle timeout.** An upload can also wait up to `render-queue-timeout-seconds` (30 s) for a render slot before rendering (up to 3 minutes), so the longest silent stretch is about 3.5 minutes; "raise it above the longest render" should say "above render-timeout plus the 30-second queue wait" (nginx's 300 s already covers this).
8. **Minor - Figure 40.4 versus Section 37.17.** The chapter says Figure 40.4 "extends" Figure 37.2, but its step numbers (1 Secrets, 2 RDS, 3 S3, 4 ElastiCache, 5 jobs, 6 ALB, 7 alarms) differ from 37.17's numbering (1 sessions, 2 counters, 3 tiles, 4 jobs, 5 secret, 6 front door, 7 deploys), and Table 40.1's "Plan step" column uses 37.17's numbers. A reader will confuse "step 3". Say once "Figure 40.4's numbers are new, not Chapter 37's", or use letters.
9. **Minor - Terms used before defined:** "sidecar" (40.14 and the solution to 40.2), "idempotent" (40.11), "Valkey" and "Redis OSS" (Table 40.1: one clause), "Lua script" (40.10: it says Redis runs it atomically, which is enough), "Object Lock" (defined in a clause), "OpenID Connect" (40.16: one clause), "fails open" (40.5: explained by the next words), "vCPU".
10. **Minor - Exercise 40.1** asks "which one of the four the project could adopt first"; the solution answers with Secrets Manager plus RDS then S3, i.e. several. Say "which of the four (or which two)".
11. **Minor - Exercise 40.5** premise ("the janitor job only lists and deletes") is consistent with the solution, but the chapter (40.8) also has the service delete old versions; say so in the exercise so the service role's `DeleteObject` is not a surprise.
12. **Minor - length and pacing.** About 8,300 words, the longest chapter in the book (Chapter 30 is about 8,000). The Beginner tier (40.1 to 40.4) is right-sized; Sections 40.12 to 40.19 are dense and could each lose a paragraph; 40.17's Terraform excerpt (a 50-line listing) is illustrative and long; the chapter's own advice ("you don't need all seven") suggests shortening the later sections.
13. **Minor - headers.** Both the chapter and the Part VII introduction still say `status: draft`; the editor owns the change. The Part VII introduction's table caption is absent (a table with no caption) and its header comment says `tag: book-m6-final` while other part openers say `tag: none`; make them consistent.
14. **Minor - tone.** Honest throughout: hedges ("this chapter did not verify") appear in the right places (Lua support on ElastiCache, session events on a managed cache, Tomcat's keep-alive default). One overclaim to soften: 40.19 lists "no single machine holds everything" as an improvement, but the app is still a single logical writer to one database primary and one shared secret; say "no single application host".
